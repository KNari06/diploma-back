Rate limiting configuration, limits per endpoint, throttling mechanisms, and rate limit errors

📋 Overview

Rate limiting protects the API from abuse and ensures fair resource usage. The system implements different rate limiting strategies for different user types and endpoints.

Key Features:

  • Anonymous User Limits: Stricter limits for unauthenticated users
  • Authenticated User Limits: Higher limits based on subscription plan
  • Endpoint-Specific Limits: Different limits for different actions
  • Automatic Reset: Limits reset automatically based on time windows

🔒 Anonymous User Rate Limiting

Limit: 3 chat messages per 24 hours

Reset: Automatically after 24 hours from first request

Scope: Only applies to anonymous (unauthenticated) users

Implementation: Database-based tracking in anonymous_usage_limits table

How It Works

  1. Anonymous user identified by anonymous_id (format: project_{projectId})
  2. Each chat request increments request_count
  3. If request_count >= 3, returns 429 RATE_LIMIT_EXCEEDED
  4. Limit resets automatically after 24 hours from first_request_at
  5. After authentication, limit is reset and user gets full access

Database Schema

anonymous_usage_limits:
  - id: UUID
  - anonymous_id: TEXT (UNIQUE)
  - request_count: INTEGER
  - last_request_at: TIMESTAMP
  - first_request_at: TIMESTAMP

Error Response

{
  "success": false,
  "error": "Rate limit exceeded",
  "code": "RATE_LIMIT_EXCEEDED",
  "details": "Anonymous users are limited to 3 chat messages per 24 hours. Please sign up for unlimited access.",
  "timestamp": "2024-01-01T00:00:00.000Z"
}

⚙️ Global Rate Limiting Configuration

Status: Currently disabled (using custom rate limiters per feature)

Configuration: Environment variables

Variable Default Description
RATE_LIMIT_WINDOW_MS 900000 (15 minutes) Time window for rate limiting
RATE_LIMIT_MAX_REQUESTS 100 Maximum requests per window

Note: Global rate limiting is currently disabled in favor of feature-specific rate limiters. To enable, uncomment the rate limiter middleware in src/index.ts.

⚠️ Rate Limit Error Response

When rate limit is exceeded, the API returns:

HTTP/1.1 429 Too Many Requests
Content-Type: application/json

{
  "success": false,
  "error": "Rate limit exceeded",
  "code": "RATE_LIMIT_EXCEEDED",
  "details": "Anonymous users are limited to 3 chat messages per 24 hours. Please sign up for unlimited access.",
  "timestamp": "2024-01-01T00:00:00.000Z"
}

Response Headers

  • X-RateLimit-Limit - Maximum requests allowed (e.g., 3)
  • X-RateLimit-Remaining - Remaining requests (e.g., 0)
  • X-RateLimit-Reset - Unix timestamp when limit resets
  • Retry-After - Seconds to wait before retrying

💡 Best Practices

  • Handle 429 Errors: Implement exponential backoff when receiving rate limit errors
  • Check Headers: Use X-RateLimit-Remaining to track remaining requests
  • Respect Retry-After: Wait for the specified time before retrying
  • Authenticate for Higher Limits: Sign up to get unlimited access
  • Monitor Usage: Track your request count to avoid hitting limits
