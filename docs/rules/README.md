# 📋 Project Rules & Guidelines

Этот документ содержит все правила и рекомендации для проекта QAI Backend.

## 🎯 Общие принципы

### 1. **Качество кода**
- Код должен быть читаемым и понятным
- Следуйте принципам SOLID
- Избегайте дублирования кода (DRY)
- Используйте осмысленные имена переменных и функций

### 2. **Безопасность**
- Никогда не коммитьте секреты в код
- Валидируйте все входные данные
- Используйте HTTPS везде
- Регулярно обновляйте зависимости

### 3. **Производительность**
- Оптимизируйте запросы к базе данных
- Используйте кэширование где возможно
- Избегайте блокирующих операций
- Мониторьте производительность

## 📝 Стандарты кодирования

### TypeScript
- Используйте строгую типизацию
- Избегайте `any` - используйте конкретные типы
- Документируйте сложные функции с JSDoc
- Следуйте принципам SOLID

### Именование
- **Файлы**: kebab-case (`user-service.ts`)
- **Классы**: PascalCase (`UserService`)
- **Функции/переменные**: camelCase (`getUserById`)
- **Константы**: UPPER_SNAKE_CASE (`API_BASE_URL`)
- **Интерфейсы**: PascalCase с префиксом I (`IUserData`)

### Структура файлов
```
src/
├── api/           # API маршруты
├── config/        # Конфигурация
├── db/            # База данных
├── jobs/          # Обработчики очередей
├── services/      # Бизнес-логика
├── types/         # TypeScript типы
├── utils/         # Утилиты
└── worker/        # Воркер очередей
```

## 🧪 Тестирование

### Обязательные тесты
- **Unit тесты** для всех сервисов и утилит
- **Integration тесты** для API endpoints
- **Покрытие кода** должно быть > 80%

### Запуск тестов
```bash
npm test              # Запуск всех тестов
npm run test:watch    # Тесты в watch режиме
npm run test:coverage # Покрытие кода
```

## 🔄 Git Workflow

### Ветки
- `main` - продакшн код
- `develop` - разработка
- `feature/feature-name` - новые функции
- `fix/bug-description` - исправления
- `hotfix/urgent-fix` - критические исправления

### Коммиты
Используйте [Conventional Commits](https://www.conventionalcommits.org/):

```bash
feat(api): add user authentication endpoint
fix(auth): resolve JWT token validation
docs: update API documentation
refactor(service): simplify user creation logic
```

### Pull Requests
- Минимум 1 одобрение для merge
- Все PR должны пройти CI/CD проверки
- Исправляйте замечания в течение 48 часов
- Будьте вежливы и конструктивны

## 🚫 Что НЕ делать

- ❌ Не коммитьте `.env` файлы
- ❌ Не добавляйте зависимости без обсуждения
- ❌ Не изменяйте API без версионирования
- ❌ Не игнорируйте ошибки линтера
- ❌ Не создавайте большие PR (> 500 строк)
- ❌ Не используйте `any` без крайней необходимости
- ❌ Не оставляйте `console.log` в продакшн коде

## ✅ Что делать

- ✅ Регулярно обновляйте зависимости
- ✅ Используйте `npm audit` для проверки уязвимостей
- ✅ Валидируйте все входные данные
- ✅ Используйте принцип наименьших привилегий
- ✅ Пишите тесты для новой функциональности
- ✅ Документируйте сложную логику
- ✅ Используйте TypeScript строго

- Используйте Winston для структурированного логирования

## 🔒 Безопасность

### Секреты
- Используйте environment переменные
- Никогда не коммитьте API ключи
- Ротируйте секреты регулярно
- Используйте разные секреты для разных окружений

### Валидация
- Валидируйте все входные данные
- Используйте Zod для схем валидации
- Санитизируйте пользовательский ввод
