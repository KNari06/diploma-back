1. Проблема и контекст

У нас есть mobile-тестирование (Android / iOS / Flutter). Юзеры записывают тест-кейсы и хотят:

  • Запускать их в регрессии последовательно (в коде MAX_MOBILE_IN_FLIGHT=1)
  • Чтобы тест "edit profile" мог стартовать с уже залогиненного состояния — без переписывания логина в каждом тесте
  • Чтобы при поломке одного теста не валилась вся регрессия
  • Чтобы регрессия не занимала час из-за 50 логинов подряд

Это классическая дилемма test orchestration на mobile, где:

  • Нельзя сериализовать app state (как storageState.json на вебе)
  • Каждое приложение имеет дерево навигации с глубиной 3-5 экранов
  • Login занимает 15-30 секунд
  • State приложения не предсказуем после краша или флака
Документ — это не план реализации. Это сравнение 4 вариантов архитектуры, чтобы команда могла выбрать. Каждый вариант разобран по факту кода — что есть, что надо добавить, что сломается.

3. Две ментальные модели юзера

Из обсуждения с командой и анализа реальных запросов:

Модель 1 — "Цепочка"

Юзер думает в терминах user journey:

login → home → profile → edit → logout

Каждый тест — это шаг в реальном flow юзера. Они связаны. State течёт.

Естественно для mobile

Модель 2 — "Дерево"

Юзер думает в терминах состояний экранов:

Home разветвляется на Cart, Profile, Settings. Каждый тест проверяет свою ветку из общей точки.

Естественно для приложений с навигацией

Обе модели валидны. Цепочка хороша для линейных flow (onboarding, checkout). Дерево хорошо для приложений с hub-screen (соцсети, маркетплейсы). Реальный продукт имеет и то и другое.

4. Вариант A — Scenarios (текущая модель)

Идея: каждый тест полностью изолирован. Общий пролог выносится в именованный scenario_setup ресурс. Перед каждым тестом проигрывается заново.

📦 Scenario "logged-in" (login + open home) ════════════════════ │ │ │ ┌─────┘ │ └──────────┐ ▼ ▼ ▼ Test "cart" Test "profile" Test "settings" pm clear pm clear pm clear + scenario + scenario + scenario + steps + steps + steps ✅ ✅ ❌ (упал на assert) → не влияет на другие
pm clear (reset) scenario test steps failed

4.1 Жизненный цикл

Регрессия из T1, T2, T3:

T1 (cart):     pm clear → launch → проиграть S1 → open cart    → assert
T2 (profile):  pm clear → launch → проиграть S1 → open profile → assert
T3 (settings): pm clear → launch → проиграть S1 → open settings → assert

Total: 3 × (pm clear + launch + scenario S1) + 3 × test steps

4.2 Что нужно в коде

Готово Backend: scenario_setup adapter, recursive use_setup, mobile compiler. scenario-setup-expander.ts

Не готово Frontend: UI для inline preview scenario в редакторе теста, "Extract last N steps to scenario", management dialog.

4.3 Плюсы / Минусы

ПлюсыМинусы
  • Полная изоляция — падение одного теста не трогает другие
  • Параллельность возможна в будущем (на 5 девайсах = 5x speed)
  • Тест можно запустить в одиночку (debug, hotfix)
  • DRY: правка scenario чинит все консумеры
  • Известная модель (Mabl flows, Tosca, Maestro subflows)
  • Performance: 50 тестов → 50 логинов
  • Глубокие scenarios (создать 5 заказов) дорогие на повторе
  • Юзер должен учиться абстракции "scenario"
  • Терминология "setup" непонятна неинженерам → переименовать в "Scenario"

5. Вариант B — Sequential Chain

Идея: тесты идут строго последовательно. State приложения переходит от теста к тесту. Между ними нет reset. Один pm clear в начале.

┏━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┓ ┃ pm clear → launch app (один раз на всю цепочку) ┃ ┃ ↓ ┃ ┃ Test "login" ──┐ (app state переходит — без reset) ┃ ┃ ↓ ✅ ↓ ┃ ┃ Test "home" ──┐ ┃ ┃ ↓ ✅ ↓ ┃ ┃ Test "profile" ─┐ ┃ ┃ ↓ ❌ failed ┃ ┃ Test "edit" SKIP (cascade) ┃ ┃ Test "logout" SKIP (cascade) ┃ ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┛

5.1 Жизненный цикл

Регрессия из T1..T5 (sequential chain):

[pm clear once]
T1 (login):   проиграть шаги  → assert  (app в состоянии "Home")
T2 (home):    проиграть шаги  → assert  (app в состоянии "Profile menu")
T3 (profile): проиграть шаги  → ❌ FAIL
T4 (edit):    SKIP — prerequisite failed
T5 (logout):  SKIP — prerequisite failed

Total: 1 × pm clear + 3 × test steps

5.3 Плюсы / Минусы

ПлюсыМинусы
  • Performance: 1 login на 50 тестов
  • Естественная mental model — список действий по порядку
  • Не надо учить новую абстракцию "scenario"
  • Cause-effect виден в логе: "profile упал → 2 skipped"
  • Cascade failure: один флак в начале → весь хвост skipped (юзер думает что 5 багов вместо 1)
  • Нельзя запустить один тест в одиночку — нужны все предыдущие
  • Параллельность невозможна (фундаментально)
  • Дублирование login: каждая цепочка пишет login заново
  • Дерево навигации (Home → 3 кнопки) выражается плохо — становится 3 параллельных списка
  • Регрессия "только сломанное" не работает
  • State drift: между T1 и T2 что-то могло произойти случайно (push notification, system dialog) — T2 стартует не там где ожидал
Главный риск: cascade failure — известная проблема Selenium IDE и старого Postman chain'а. Cypress, Playwright, Maestro сознательно ушли от этой модели на test isolation именно потому что одно случайное падение делает регрессию бесполезной.

6. Вариант C — State Cache (scenario с кешированием состояния)

Идея: scenarios как в варианте A, но с оптимизацией: после первого успешного прогона scenario в регрессии — кешируем app state и переиспользуем для следующих тестов с тем же scenario.

📦 Scenario "logged-in" ════════════════════ │ ┌────────┴─────────────┐ ▼ ▼ Первый тест: Следующие тесты: pm clear Кеш-хит: + проиграть scenario проверить "уже на Home?" + test steps ✅ да → скип scenario ────────────── ❌ нет → проиграть scenario 💾 кеш state + test steps (snapshot экрана)

6.1 Жизненный цикл с кешем

Регрессия из T1, T2, T3, T4, T5 (все используют scenario "logged-in"):

T1: pm clear → проиграть scenario → ✅ запомнить "state X: logged-in достигнут"
                                  → проиграть шаги T1 → assert
T2: проверить "state X достигнут?" → ❌ нет (T1 закончился на /profile, не на /home)
    → pm clear → проиграть scenario → проиграть шаги T2

Альтернативный сценарий: тесты не меняют core state
T1: pm clear → scenario → "user is logged in"
              → шаги T1 (только GET-запросы) → assert
T2: scenario.validate() = "user is still logged in" ✅ → скип scenario → шаги T2
T3: scenario.validate() = ✅ → скип scenario → шаги T3
...

6.2 Как реализовать validate

Каждый scenario имеет validate-шаг (опционально, добавляется юзером в UI):

Scenario "logged-in":
  Steps:
    - tap "Login"
    - type email
    - type password
    - tap "Submit"
  Validate (опциональный, новое поле):
    - assert visible: "Welcome, {user.name}"
    - assert URL contains: "/home"

Перед запуском scenario в следующем тесте:
  if validate() == true → SKIP scenario steps
  else → проиграть scenario заново

6.4 Плюсы / Минусы

ПлюсыМинусы
  • Best of both: performance как chain + isolation как scenarios
  • Юзер может отключить кеш чекбоксом если флаки
  • Validate-шаг ловит drift автоматически (Cypress cy.session({validate}) паттерн)
  • Падение одного теста не трогает других — но scenario сыграется заново только если validate упадёт
  • Параллельность остаётся возможной
  • Нужно учить юзера писать validate (но это 1 строка: "assert visible: Home Title")
  • Если validate слабый — кеш врёт ("я залогинен" но cookie протух → тест упадёт на 5-м шаге с непонятной причиной)
  • Между regression runs кеш сбрасывается (новая сессия пула)
  • Нужно решить — кешировать через session pool или через snapshot
Это самый близкий аналог Cypress cy.session({validate}), перенесённый на mobile. Cypress — единственный инструмент, который успешно решил drift через validate. Все остальные либо игнорируют drift (Mabl, Tosca), либо отказываются от reuse (Maestro).

7. Вариант D — Hybrid Test Suite рекомендуемый

Идея: ввести новую сущность Test Suite с флагом sequential. Юзер сам решает: писать тесты как изолированные (с scenarios) или как цепочку. Внутри suite можно использовать оба подхода.

7.3 Можно ли добавить State Cache (Вариант C) к Hybrid?

Да, и это лучший вариант. Для parallel suite scenarios могут иметь validate-шаг. Если runner запускает несколько тестов одной suite в pool — кеш работает между ними. Для sequential suite кеш не нужен (state уже там по построению).

Финальная рекомендация: Hybrid Test Suite (D) + опциональный State Cache (C) для parallel suites. Это покрывает все три ментальные модели юзера, даёт performance, сохраняет isolation как fallback.

9. Failure modes — что ломается и как починить

9.1 Cascade failure (Вариант B)

Симптом: один флакающий тест в середине → 20 skipped тестов. Юзер видит "профиль сломан" + "редактирование сломано" + "logout сломан" — думает что у него 3 бага, на самом деле один.

Митигация: в UI явно показывать: "Skipped because 'profile' failed — not a real failure". В regression report — группировать по cause.

Полное решение: retry-логика для всей цепочки. Если test упал — повторить с начала suite (дорого, но единственный надёжный fix).

9.2 Drift между scenario и приложением (Вариант A, C)

Симптом: кто-то поменял UI login flow. Scenario "logged-in" больше не работает. 50 тестов одновременно падают с "element 'email field' not found".

Митигация: validate-шаг в конце scenario (Вариант C). Если validate упал — clear лог "scenario broken, fix this first" вместо 50 одинаковых failures.

Дополнительно: alert юзеру при сохранении scenario: "Этот scenario используют 12 тестов — проверьте что не сломали".

9.3 State cache врёт (Вариант C)

Симптом: validate говорит "OK, ты на home", но сессия протухла (cookie expired). Тест T2 стартует, кликает "Add to cart" → редирект на login → fail с непонятной причиной.

Митигация: validate должен проверять не только видимость элемента но и функциональность. Пример: вместо "see Welcome text" — проверка "click profile icon → profile screen visible". Тяжелее но надёжнее.

Fallback: если 2 теста подряд упали на первом шаге после cache hit — автоматически invalidate cache и проиграть scenario заново.

9.4 Глубокий scenario неэффективен (Вариант A)

Симптом: Тест "delete order" требует scenario "user has 5 orders". Это 2 минуты setup. На регрессии из 5 тестов order-feature → 10 минут на setup, 30 секунд на сами тесты.

Митигация в A: ничего, медленно по построению.

Митигация в C: validate "user has at least 5 orders" → если да, скип scenario.

Митигация в D: sequential suite "Order management" — создал 5 orders один раз, прогнал все order-тесты подряд.

9.5 Pool session pollution (Варианты B, C, D)

Симптом: sequential suite закончилась failed, app в непредсказуемом state. Следующая регрессия клеймит ту же сессию из pool — стартует в каком-то модальном окне.

Митигация: после failed sequential suite — destroy session, не release. Это уже частично есть в коде (mobile-test-run.job.ts:1046-1051).

9.6 Push notification / system dialog (все варианты)

Симптом: в середине теста OS показала "App wants to send notifications" overlay. Все последующие клики промахиваются.

Митигация: универсальный obstacle handler в runner (mobile-runner-client уровень). Это вне scope этого документа но критично для любого варианта.

15. Аддендум — детали из обсуждения

Этот раздел собирает важные детали, которые всплывали в обсуждении и которые легко упустить при чтении основной части.

15.1 Концепция "первый шаг / последний шаг" как entry/exit state

В обсуждении возникла идея: "первый шаг теста — это его entry state, последний шаг — exit state. Тест B стартует там, где кончился A."

Это правильная UX-интуиция, но индустрия не моделирует это напрямую. Вместо этого:

  • Entry state = декларация "я работаю в состоянии X" → реализуется через scenario_setup binding
  • Exit state = финальный assertion теста → может стать validate для другого scenario через extract

Иначе говоря: твой "последний шаг A" не становится "первым шагом B" напрямую. Он может стать validate-проверкой для scenario, который используют оба теста.

Тест A: ... → последний шаг: assert visible "Cart screen" │ ↓ extract как validate │ 📦 Scenario "in-cart" Steps: login + add item to cart Validate: assert visible "Cart screen" │ ↓ используется │ Тест B: scenario "in-cart" → шаги B (checkout flow)

15.2 Drift между scenario и source test

Когда юзер делает extract из теста A → scenario S, в момент извлечения S = последние N шагов A. Через 2 недели:

  • Кто-то добавил в тест A шаг "accept cookies"
  • Scenario S остался без него
  • Тест B использует S → может упасть на cookie-banner
ИнструментКак решает
MablEdit-once-propagate — при правке flow обновляются все консумеры (но изменения теста-донора в flow НЕ попадают)
ToscaReference-based — то же что Mabl, та же проблема
TestRailShared Steps — те же грабли
Cypresscy.session({validate}) — единственный кто ловит drift в runtime
Для нас (рекомендация)При save теста-донора показывать diff: "Этот тест отличается от извлечённого из него scenario X на 2 шага. Обновить scenario?"

15.3 AI Auto-Suggest Extract — Testim Auto Grouping pattern

Testim это единственный инструмент, который делает AI-driven extraction. Их паттерн:

  1. Фоновая задача периодически анализирует все тесты в проекте
  2. Ищет повторяющиеся последовательности шагов
  3. Предлагает extract в named group
  4. После accept — auto-replace во всех найденных местах с diff preview

У нас есть инфраструктура для этого:

  • intent_test_cases.steps_json — все шаги всех тестов в БД
  • src/services/ai/embeddings/ — embedding пайплайн уже работает
  • Можно прогнать pairwise similarity prefix-шагов всех тестов

При сохранении нового теста — сравнить с проектом, если найдены 2+ теста с похожим префиксом → suggest "Extract first 4 steps as scenario? (5 tests would benefit)".

Сложность: 1-2 недели. Это killer feature, не делается в Phase 1, но архитектурно надо предусмотреть.

15.4 Validate timing — "before scenario" vs "after scenario"

В Cypress cy.session({validate}) работает в двух точках:

  1. Before scenario — "перед тем как играть scenario, проверь — может состояние уже достигнуто?". Если да → скип scenario.
  2. After scenario — "после прогона scenario проверь что состояние действительно достигнуто". Если нет → fail рано, до запуска теста.

В документе варианта C упомянуто только #1 ("skip if validate passed"). #2 не менее важен — без него scenario может молча "сыграть" но не привести в нужное состояние, и тест упадёт на первом шаге с непонятной причиной.

Рекомендация: оба. UX:

Scenario "logged-in":
  Steps: [login flow]
  Validate (runs both before and after):
    ✓ assert visible "Home Title"
    ✓ assert URL contains "/home"

Run-log:
  T1: Scenario "logged-in" — validate before: ❌ not in state → run steps → validate after: ✅
  T2: Scenario "logged-in" — validate before: ✅ in state → SKIP steps
  T3: Scenario "logged-in" — validate before: ❌ → run steps → validate after: ❌
       → STOP, mark scenario as broken, fail T3 cleanly

15.5 Почему web-подход (storageState) не работает на mobile

На вебе Cypress/Playwright сериализуют сессию в storageState.json: cookies + localStorage + IndexedDB. Файл маленький (KB), сериализация — миллисекунды, restore — быстрый.

На mobile это невозможно по техническим причинам:

ПлатформаЧто хранит stateСериализация
Android /data/data/<package>/: shared_prefs (XML), sqlite, files, cache + activity stack в RAM adb backup -f file.ab — 10-100 MB на тест, занимает 5-30 секунд, ломается при app update, не покрывает RAM state
iOS App sandbox: NSUserDefaults, CoreData, Keychain Без jailbreak — невозможно. С jailbreak — нестабильно.
Flutter Зависит от платформы под Flutter Те же ограничения что Android/iOS

Вывод: вариант "снэпшот state теста A → restore перед тестом B" технически нереализуем для mobile в 2026. Единственный путь — прогнать setup steps заново (вариант A) или не делать pm clear между тестами в suite (вариант B/D).

15.6 executed_resources — audit trail для отладки

У нас в БД уже есть колонка test_executions.executed_resources (JSONB). Сейчас она пишется после каждого теста (mobile-test-run.job.ts:1491).

Для вариантов C/D эта колонка становится критичной для отладки:

{
  "scenarios": [
    {
      "id": "uuid-of-logged-in",
      "name": "logged-in",
      "status": "skipped_validate_passed",   // executed | skipped_validate_passed | failed_validate
      "validate_duration_ms": 542,
      "steps_skipped_count": 4,
      "cache_source": "previous_test_in_run" // или "session_pool" или "none"
    }

}

Это позволит юзеру понять "почему этот тест прошёл за 10 секунд а соседний за 45" — увидеть что в первом scenario скипнулся, во втором сыграл.

15.7 Retry semantics для sequential suite

Если suite "Onboarding flow" падает на тесте 3 из 4 — что делать?

ОпцияПоведениеPros / Cons
No retry Тесты 4 помечается skipped, suite failed. ✅ Простой, ❌ один флак ломает результат
Retry from failed test Тест 3 повторяется. Если прошёл — продолжить с 4. ✅ Простой fix для флака. ❌ Проблема: тест 3 теперь стартует не из состояния "после теста 2" а из "после неудачной попытки теста 3" — может быть другой state.
Retry from start of suite Pm clear + проиграть с самого начала. ✅ Гарантирует чистый state. ❌ Дорого: если suite 30 минут — retry стоит 30 минут.
Retry only test 3 in isolation Pm clear + проиграть scenario binding теста 3 + сам тест 3. ✅ Дёшево. ❌ Работает только если тест 3 имеет scenario binding.

Рекомендация: опция "Retry from start of suite" с лимитом 1 повтор. Это match'ит Maestro Cloud retry. По умолчанию выключено, юзер включает в настройках suite.

15.8 Web vs Mobile asymmetry

Web tests сейчас работают по варианту A (scenarios). На вебе:

  • storageState.json уже даёт быстрый login без UI (1-2 секунды)
  • Изоляция тестов дёшева — новый browser context за 200ms
  • Параллельность лёгкая — несколько браузеров одновременно

Mobile:

  • Login через UI занимает 15-30 секунд
  • Изоляция через pm clear — 5-10 секунд
  • Параллельность дорогая — нужны отдельные эмуляторы

Это значит: вариант D (Hybrid Suite) может быть только для mobile. На вебе sequential suite не даёт большой выгоды, добавляет сложность. Команде стоит решить осознанно — расходимся ли мы по платформам.

15.9 Конкретные performance numbers

Регрессия из 50 тестов, у каждого scenario "logged-in" (30 сек login):

ВариантApp setupScenario playsTest stepsTotal (приблизит.)
A: Scenarios as-is 50 × 8s = 400s 50 × 30s = 1500s 50 × 20s = 1000s ~48 минут
B: Sequential Chain 1 × 8s = 8s 1 × 30s = 30s (login один раз) 50 × 20s = 1000s ~17 минут
C: Scenarios + Cache (hit rate 90%) 50 × 8s = 400s 5 × 30s + 45 × 1s = 195s 50 × 20s = 1000s ~27 минут
D: Hybrid (1 seq suite + 40 parallel with cache) 1 × 8s + 40 × 8s = 328s 1 × 30s + 4 × 30s = 150s 50 × 20s = 1000s ~25 минут

Вывод по перфомансу: sequential chain в чистом виде даёт самый большой выигрыш по времени, но цена — cascade failure и потеря isolation. C даёт почти то же время при сохранении isolation. D балансирует.

15.10 Что мы НЕ обсудили (на будущее)

  • Conditional scenarios — "если юзер новый — onboarding, если старый — skip". Появится позже.
  • Cross-platform scenarios — один scenario для Android и iOS? Сейчас platform-locked, может остаться так.
  • Scenarios as test prerequisites — в UI показать "этот scenario используют 12 тестов, любое изменение их затронет" как Tosca делает.
  • Visualization graph — DAG-граф зависимостей tests↔scenarios. Полезно для аудита, но не для повседневного редактирования.
