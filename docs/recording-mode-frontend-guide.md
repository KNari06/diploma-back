# Recording Mode — Frontend Integration Guide

## Overview

Recording mode captures real user interactions on the preview browser and automatically generates test steps. When the user presses the "Rec." button, every click, keystroke, scroll, and select action is transformed into an `IntentStep` and sent to the frontend in real-time via WebSocket.

The frontend is responsible for:
- Toggling recording on/off via the "Rec." button
- Listening for incoming recorded steps and appending them to the step list
- Showing a transient element highlight when a step is captured
- Reflecting recording state in the UI (active indicator, button state)
- Handling edge cases where recording stops automatically (page reset, run start)

---

## WebSocket Events

### Client → Server

| Event | Payload | Description |
|---|---|---|
| `preview:recording:start` | `{ previewSessionId }` | Start recording. Backend confirms with `preview:recording:state`. |
| `preview:recording:stop` | `{ previewSessionId }` | Stop recording. Backend flushes pending buffers, emits any remaining steps, then confirms with `preview:recording:state`. |

### Server → Client

| Event | Payload | Description |
|---|---|---|
| `preview:recording:state` | `{ previewSessionId, recording, timestamp }` | Confirms recording started or stopped. Can also arrive unprompted (see Auto-Stop below). |
| `preview:recording:step` | `{ previewSessionId, step, highlight?, timestamp }` | A new recorded step. Append to the step list. |

---

## Payload Shapes

### PreviewRecordingRequest (client → server)

| Field | Type | Required | Description |
|---|---|---|---|
| `previewSessionId` | string | yes | The active preview session ID |

### PreviewRecordingStatePayload (server → client)

| Field | Type | Description |
|---|---|---|
| `previewSessionId` | string | Session this state belongs to |
| `recording` | boolean | `true` = recording is active, `false` = recording is stopped |
| `timestamp` | string | ISO 8601 timestamp |

### PreviewRecordingStepPayload (server → client)

| Field | Type | Description |
|---|---|---|
| `previewSessionId` | string | Session this step belongs to |
| `step` | PreviewIntentStep | The recorded step (same shape as manually-created steps) |
| `highlight` | PreviewBoundingBox (optional) | Bounding box of the interacted element, for transient visual highlight |
| `timestamp` | string | ISO 8601 timestamp |

### PreviewIntentStep (within step payload)

Recorded steps use the same `PreviewIntentStep` interface that already exists for manually-authored steps. Key fields:

| Field | Type | Description |
|---|---|---|
| `id` | string | Unique ID, prefixed with `rec_` (e.g., `rec_a1b2c3d4`) |
| `type` | string | Action type: `click`, `type`, `press`, `scroll`, `check`, `uncheck`, `open`, `close`, `toggle`, `select`, `wait_for` |
| `description` | string | Human-readable description (e.g., `"Click 'Sign In'"`, `"Type 'john@mail.com' in 'Email'"`) |
| `value` | string (optional) | Typed text for `type` steps, selected value for `select` steps |
| `bindingHints` | object (optional) | Element matching hints: `{ role?, label?, placeholder?, nearText?, autocomplete?, type? }` |
| `options` | object (optional) | Step options. Present on auto-generated `wait_for` steps with `urlMatcher.changedFrom` |

### PreviewBoundingBox (within highlight)

| Field | Type | Description |
|---|---|---|
| `x` | number | Left edge (px, relative to viewport) |
| `y` | number | Top edge (px) |
| `width` | number | Width (px) |
| `height` | number | Height (px) |

## Step Types Generated by Recording

| User Action | Generated `step.type` | `step.description` Example | `step.value` |
|---|---|---|---|
| Click button | `click` | `"Click 'Sign In'"` | — |
| Click checkbox (unchecked) | `check` | `"Check 'Remember me'"` | — |
| Click checkbox (checked) | `uncheck` | `"Uncheck 'Remember me'"` | — |
| Click accordion (closed) | `open` | `"Open 'Details'"` | — |
| Click accordion (open) | `close` | `"Close 'Details'"` | — |
| Click toggle button | `toggle` | `"Toggle 'Dark mode'"` | — |
| Type in input field | `type` | `"Type 'john@mail.com' in 'Email'"` | Full typed text |
| Press Enter / Tab / Escape | `press` | `"Press Enter"` | — |
| Press with modifier | `press` | `"Press Ctrl+A"` | — |
| Select option from `<select>` | `select` | `"Select 'Kazakhstan' in 'Country'"` | Selected option value |
| Scroll | `scroll` | `"Scroll down"` or `"Scroll up"` | — |
| Click that triggers navigation | `click` + `wait_for` | Click step, then `"Auto: wait for URL change"` | — |

## Integration Flow

### 1. Starting Recording

When the user taps the "Rec." button:

1. Emit `preview:recording:start` with `{ previewSessionId }`
2. Wait for `preview:recording:state` with `recording: true`
3. Update UI: activate recording indicator, change button to "Stop" state
4. Begin listening for `preview:recording:step` events

If the session is not found or not owned by the user, the server emits an `error` event with code `FORBIDDEN`.

If recording is already active, the server silently ignores the request (no error, no duplicate state event).

### 2. Receiving Recorded Steps

For each `preview:recording:step` event:

1. Extract `step` from the payload
2. Append it to the step list in the UI (same way as manually-added steps)
3. Recorded steps have `id` prefixed with `rec_` — use this to distinguish them visually if desired
4. If `highlight` is present, show a brief overlay/flash on the preview viewport at the given bounding box coordinates. The highlight should auto-dismiss after ~500-800ms. The coordinates are relative to the page viewport (same coordinate space as the preview canvas).
5. Scroll the step list to reveal the newly added step

### 3. Stopping Recording

When the user taps "Stop" (or the Rec. button again):

1. Emit `preview:recording:stop` with `{ previewSessionId }`
2. Wait for `preview:recording:state` with `recording: false`
3. Between the stop request and the state confirmation, the server may emit **remaining buffered steps** (pending typing or scroll). Append these normally.
4. Update UI: deactivate recording indicator, restore button to "Rec." state

### 4. Typing Behavior

Typing is **debounced** on the backend. The user types multiple characters, and after 1500ms of inactivity the server emits a single `type` step with all accumulated text.

This means:
- The frontend does NOT receive a step per keystroke
- A `type` step arrives ~1.5 seconds after the user stops typing, or immediately when the user clicks elsewhere / presses Enter / Tab / Escape
- The `step.value` contains the complete accumulated text

The frontend should handle this naturally — just append the step when it arrives.

### 5. Scroll Behavior

Scroll events are also **debounced** (500ms). Multiple scroll wheel events within 500ms produce a single `scroll` step. Direction is determined by the total accumulated delta: positive = "Scroll down", negative = "Scroll up".

### 6. Navigation Detection

When a click causes a page navigation (URL change), the server emits **two steps** in sequence:

1. A `click` step (the click itself)
2. A `wait_for` step with description `"Auto: wait for URL change"` and `options.urlMatcher.changedFrom` set to the previous URL

Both steps arrive as separate `preview:recording:step` events. The `wait_for` step ensures that during replay, the system waits for navigation to complete before continuing.

## Auto-Stop Scenarios

Recording stops automatically in these cases. The frontend must listen for unprompted `preview:recording:state` with `recording: false` and update the UI accordingly.

| Trigger | What Happens |
|---|---|
| **Page reset** (`preview:page:reset`) | Recording stops. Pending typing buffer is flushed (step emitted) before reset. State event sent after reset completes. |
| **Run start** (`preview:run:start`) | Recording stops to prevent duplicate steps from replay. Pending buffers flushed, state event sent. |
| **Disconnect** | Recording timers are cleaned up server-side. No state event (socket is gone). |

The frontend must NOT assume recording is still active after a page reset or run start. Always trust the `preview:recording:state` event as the source of truth.

## UI Requirements

### Rec. Button

- Located in the step editor toolbar (already exists, currently non-functional)
- When recording is **off**: shows "Rec." label, neutral/inactive style
- When recording is **on**: shows "Stop" label (or a visual recording indicator), active/red style, optionally with a pulsing dot or animation
- The button should be **disabled** while waiting for the state confirmation from the server (between emit and state event) to prevent double-tapping

### Step List

- Recorded steps are appended at the end of the step list, in real-time
- They use the same visual representation as manually-created steps
- Optional: add a subtle visual marker (e.g., small dot or icon) to indicate a step was recorded vs. manually authored. Use the `rec_` prefix on `step.id` to detect this.
- Auto-scroll the step list to the bottom when new steps arrive during recording
- Recorded steps are **editable** — the user can modify the description, type, or value after recording, just like manual steps

### Element Highlight

- When a `preview:recording:step` includes `highlight`, draw a transient rectangle overlay on the preview canvas at the given `{ x, y, width, height }`
- The highlight should fade out after ~500-800ms
- Use a semi-transparent color (e.g., blue or green with 30% opacity) with a solid border
- The highlight coordinates are in the same coordinate space as the preview viewport (1280x720, 1:1 scale)

### Recording State Indicator

- While recording, show a visible indicator somewhere in the step editor (e.g., a red dot in the toolbar, "Recording..." text, or a colored border)
- This should reflect the `recording` field from `preview:recording:state`, not local state

## Error Handling

| Error | When | How to Handle |
|---|---|---|
| `error` with code `FORBIDDEN` | `recording:start` on a session not owned by user | Show error toast, do not activate recording UI |
| Step arrives for wrong `previewSessionId` | Multi-session edge case | Ignore steps where `previewSessionId` doesn't match the active session |
| `recording:state` with `recording: false` arrives unexpectedly | Auto-stop (reset, run) | Update UI to reflect stopped state, show a brief info message (e.g., "Recording stopped: page was reset") |
| No `recording:state` response within ~3 seconds | Network issue or server error | Timeout locally, reset button to idle state, optionally show error |

---

## Step Ordering Guarantees

1. **Typing before click**: If the user types and then clicks, the typing step always arrives before the click step
2. **Typing before Enter/Tab**: If the user types and presses Enter, the typing step arrives before the press step
3. **Click before navigation**: If a click triggers navigation, the click step arrives before the `wait_for` step
4. **Steps arrive in interaction order**: The server emits steps in the order they occurred. The frontend should append them in arrival order.

---

## State Management Recommendations

- Store `isRecording` as a boolean in the preview session state
- Update it ONLY when `preview:recording:state` is received (not on button click)
- Optimistically disable the button on click, re-enable on state event or timeout
- Store recorded steps in the same array as manual steps — they are the same data type
- When recording stops, the step list contains the full sequence of recorded + manual steps, ready for saving

---

## Not Recorded (by design)

These actions are NOT captured during V1 recording:

- **Hover** — mouse move is too frequent, no reliable way to detect intentional hover
- **Drag and drop** — complex mouse:down → move → mouse:up sequences, not yet supported
- **File upload** — requires separate UI flow
- **Manual step apply** (`preview:step:apply`) — these are already-authored steps, not user interactions
- **Run replay** (`preview:run:start`) — recording stops automatically when a run begins
- **wait / assert / ai_check** — these require human judgment and cannot be inferred from interactions
